### B. Core vocabulary (WP0.2)

**B1. `spec/VOCABULARY.md`** defines every term the schemas will use. For each term: one-sentence meaning, allowed values where it is an enumeration, and one example. Sections, in this order:

1. File kinds: `model-config`, `source`, `entity`, `service`, `tenants`, `evidence`, `finding`, `escalation`, `hazard`, `decision`, `profile`, `layer`, `consumer`, `release-allowlist`, `probe`, `probe-result`, `trigger`.
2. Identifiers: slug rule `^[a-z0-9][a-z0-9_-]{0,63}$`; entity `id` vs `physical_name`; relationship reference `<entity-id>.<relationship-key>` (D-002); register IDs `F-0001`, `E-0001`, `H-0001`, `D-0001` - never reused, never deleted.
3. Evidence: fields (`id`, `source`, `pin`, `quote` or `measurement`, `status`, `read_on`, and for probe results `environment` and `representative: true | false | unknown`); status `confirmed | inferred | unresolved | retracted` with the exact meaning of each and who may set it (agent-authored facts start as `inferred`; `confirmed` comes from an adapter, a probe in range, or owner-read evidence); a retraction requires `named_error` and `superseded_by`. Quotes are at most 40 words.
4. Sources: kinds `git | warehouse | api | document | ticket | person`; access modes `agent_read | owner_read | export_file`; rank (integer, lower wins; default ranks per kind with a one-line reason); pin format per kind:
   - git `<repo>@<sha>:<path>[:<line>]`
   - warehouse `<engine>:<project>.<dataset>@<YYYY-MM-DD>`
   - api `<host><path>@<YYYY-MM-DD>`
   - document `<title>@<version or YYYY-MM-DD>`
   - ticket `<system>:<key>@<YYYY-MM-DD>`
   - person `<role>@<YYYY-MM-DD>` (a role, never a name)
5. Physical layer: entity class `data | configuration | administrative | reference`; entity status `draft | reviewed | deprecated`; subject scope `direct | transitive | none`; scope basis `declared_reference | unique_target | current_row_rule | measured_fanout`; relationship `key`, `meaning`, optional `discriminator`, mechanism `declared_fk | inferred_join | derivation | representation`; cardinality `one_to_one | many_to_one | one_to_many | many_to_many | unknown`; field `path` (dotted, for nested fields) and `repeated`; grain (free text, one sentence); current-row rule (what it is, when it is required); service kind `pipeline | scheduled_job | application | manual`.
5a. Tenants and environments: environment (`dev`, `test`, `prod`, free slug), tenant, and two separate facts per pair - `ingest` (what the configuration accepts) and `presence` (what the data shows). State that they are never merged into one value.
6. Derived values: list every value that is computed and must never be authored (`label`, `subject_scoped`, `reachable`, `residue`, `withheld`), and where each is written (`generated/`).
7. Profiles: anchor entity, label vocabulary, ordered rules, first match wins, `withheld` and residue.
8. Registers: finding, escalation, hazard, decision - what each is for, statuses, what closes it. State the rule: hazards are permanent semantics and are never counted as issues.
9. Semantic layers and consumers: one paragraph each; details come in M3.
10. Probes: kinds planned for M1 (key duplicates, join match and orphans, fan-out to anchor, null rate, row count); the rule that probes return counts and rates only.

**B2.** Use the spec's words. Where the spec uses two words for one thing, pick one, list the other as "not used", and fix the spec text to match.

**B3. Machine-readable blocks.** Every enumeration in VOCABULARY.md is also given as a fenced YAML block with a fixed heading pattern:

````markdown
```yaml vocabulary:entity_class
- data
- configuration
- administrative
- reference
```
````

`src/plumbline/vocabulary.py` parses all `yaml vocabulary:<name>` blocks into a dict. `tests/test_vocabulary.py` checks: every block parses; no duplicate names; no duplicate values inside a block; every value is a valid slug; the expected set of block names is present (file kinds, evidence status, representativeness, source kinds, access modes, entity class, entity status, subject scope, scope basis, mechanism, cardinality, service kind, derived values). Later schemas will import these lists, so the vocabulary has one source.

**B4. `AGENTS.md`** for this repository, invariants only, at most 40 lines: clean-room rule; English only; never commit or push; every change has a CHANGELOG entry with the reason; decisions go to `decisions/`; tests and lint must pass before a round is reported done; how to report (section 8 of this brief).
