## 1. Outcome

`fact sync --source <id>` compares the latest snapshot with the previous one and with the model. It classifies every change (eight drift kinds, four classes), writes drafts for new facts, opens findings for lost facts, fires `source_pin_moved` triggers and writes a drift report; a second run changes nothing. A new `triggers` gate stage fails on a fired trigger without follow-up; all checks are green.

## 5. Confirmed / inferred / unknown

**Confirmed**

- Every drift kind is produced and classified as the golden test expects; sync is idempotent.

**Inferred**

- A change to an object nobody has modelled is `no_effect`; its draft carries it. An object the model has but the latest snapshot does not is `lost_fact` even without a previous snapshot.
- A new field on a modelled object redrafts the whole entity in `drafts/` (the reviewer merges it).
- Lost-fact findings carry `extensions.sync_key`, so a second sync never opens the same finding twice.
- Modelled entities are matched to snapshot objects by `physical_name` and `source`.
- The trigger firing records the old and new pin in `detail`; the firing date is the latest snapshot's date.

**Unknown**

- How noisy `constraint_change` is on engines whose catalogs rename constraints between reads (compared by type, columns and target, not by name, so renames alone do not count).

## 6. Divergences

- The drift report is `generated/drift-<source-id>.md` per source, not one `generated/drift.md`, so syncing one source never erases another's report.
- Triggers stay one file per trigger (the `trigger` schema from WP0.3), not a single `maintenance/triggers.yaml`.
