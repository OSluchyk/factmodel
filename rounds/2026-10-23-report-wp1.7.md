They are generated from model facts, run through the `sql` adapter or a rendered shell script (counts only), and taken in as evidence that confirms facts in range and opens findings out of range. ## 5. Confirmed / inferred / unknown

**Confirmed**

- Counts agree between SQLite and PostgreSQL for every generated kind on the same rows.
- No probe selects a value: every select is a count, a `COUNT(DISTINCT ...)`, or a maximum of counts.

**Inferred**

- `fan_out` measures the most target rows that share one join-key value (the most rows a source row meets); generated only for `many_to_one` and `one_to_one` links, expected at most 1.
- `current_row_ties` uses the entity's first unique key, else its primary key, and reads the current-row rule as SQL in the source's dialect.
- Rates are computed at intake (`match_rate`, `null_rate`), so no probe divides in SQL.
- Evidence from a probe is `confirmed` (it is a measurement); whether the fact moves to `confirmed` depends on the range. A result with no expected range is cited as information.
- Target sets and unresolved relationships get no probe in v1; they are listed as skipped.
- Probe results files are JSON lines in `probes/results/` (not YAML), so the loader does not read them; the `probe-result` file kind stays unused for now.

**Unknown**

- Behaviour of the rendered SQL on Snowflake, DuckDB, T-SQL and MySQL engines: rendering is tested, execution is not (no engines available).

## 6. Divergences

- `fact probe generate` takes an optional default dialect for entities without a source (used for the hard cases).
- Rendered scripts wrap queries to print JSON only for SQLite and PostgreSQL; other dialects need `RUN_SQL` set to a client that prints one JSON object per query.
