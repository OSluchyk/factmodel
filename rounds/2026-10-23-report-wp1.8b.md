## 5. Confirmed / inferred / unknown

**Confirmed**

- All 19 cases give the intended verdict and generated files; the intended derived rows (for example `comments.on withheld orders=customer_scoped, products=customer_scoped, settings=configuration`) were written by hand and checked.

**Inferred**

- The plan's "key-not-unique: admission only with `current_row_rule` or `measured_fanout`" needed a rule the algorithm did not have. I read cardinality as the signal: `unique_target` requires `many_to_one` or `one_to_one`. A loader check that the target's primary key is the joined field would be stronger; not done.
- Hard cases may fail more than one stage (for example a rejected admission leaves a data entity unscoped, which the retail profile then leaves as residue). Single-stage isolation is the job of the round-6 gate fixtures.
- The "coverage note" for a nullable anchor reference is prose in `meaning` plus a hazard; there is no coverage field.

**Unknown**

- Whether the retail profile should label unscoped data to scoped data (today it is residue). This decides whether a rejected admission always also fails projection.

## 6. Divergences

- 19 cases instead of 9: ten variants make every stage fail at least once, as the brief requires.
- Two core changes beyond fixtures: `non_unique_target` (new vocabulary value, new vector) and nested-path anchor references (schema change). Neither changes a decision or a spec principle.
- Hard cases were generated by a scratch script that also checks each intended outcome; the script is not committed, the cases are.

2. Should `unique_target` also be checked against the target's keys (the join must hit its primary or a unique key)?
3. Should the retail profile get a rule for unscoped data linked to scoped data, or is residue the right signal?
