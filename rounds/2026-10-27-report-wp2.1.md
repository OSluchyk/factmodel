## 5. Confirmed / inferred / unknown

**Confirmed**

- `duckdb-engine` 0.17.0 cannot reflect columns or keys on DuckDB 1.5.6 or 2.0.0 with SQLAlchemy 2.0 or 2.1: it inherits PostgreSQL's catalog queries, and DuckDB answers neither `pg_catalog.pg_collation` nor `REGCLASS`. This is the finding the brief anticipated on the `sql` adapter.
- DuckDB's `INFORMATION_SCHEMA` gives every neutral part the tests compare (tables, views, columns, nullability, types, primary, unique and foreign keys with referenced columns).
- DuckDB enforces declared foreign keys.
- Rendered probes in the `duckdb` dialect run on DuckDB with the same counts as SQLite and PostgreSQL (45 Chinook probes).

**Inferred**

- The fallback is engine-neutral: it triggers on any SQLAlchemy reflection error, not on the engine name, and reads only standard views. It does not read comments (`TABLE_COMMENT`, `COLUMN_COMMENT` are DuckDB extensions), so descriptions are absent from DuckDB snapshots.
- System schemas `information_schema` and `pg_catalog` are excluded; DuckDB lists only user objects in practice.
- The plugin is installed as an editable path dependency of the dev group, so CI (`uv sync --locked`) gets it with no extra step.

**Unknown**

- Whether a later `duckdb-engine` release reflects natively; the fallback keeps working either way.
- `fact probe render --dialect duckdb` has no runner line in `dialect_runner`, so the rendered script uses the neutral runner placeholder; `fact probe run` through `sql` is the tested path.

## 6. Divergences

- The test package is installed by `uv sync` (path dependency of the dev group), not by `uv pip install -e` in a fixture or an `importlib.metadata` stub: the real install path is the stronger proof and needs no network.
- DuckDB reflection needed an adapter change (standard-views fallback) rather than only a recorded finding. The change lives in the `sql` adapter, not the core.
- `duckdb>=1.1` rather than `>=2.0`: both versions behave the same; the looser floor costs nothing.
