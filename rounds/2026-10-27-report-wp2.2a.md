## 5. Confirmed / inferred / unknown

**Confirmed**

- Every core change in this round is covered by D-015 or D-017 (section 4); no stop condition was hit.
- Chinook and all earlier hard cases are unchanged (their generated files and verdicts still match).
- The expression probe renders differently per dialect (`SUBSTRING(x, 1, 2)` on SQLite, `SUBSTRING(x FROM 1 FOR 2)` on PostgreSQL) and counts correctly on SQLite.

**Inferred** (choices made inside the decisions)

- `all_ends_subject_scoped` is forbidden with `any_end_subject_scoped` and `subject_scoped`: the brief names two, but the third has the same problem.
- A top-level conjunct that reads one end only is a filter on that end (`substr(areas.area_fips, 3, 3) <> '000'`: the source is a county). It restricts `source_rows` and `orphans_left`, and is ignored by the `unique_target` rule. Written into D-017 before the record was committed.
- `fan_out` for an expression groups the target by the target operands of the equalities between the ends; with any other comparison between the ends there is no `fan_out`.
- Expression joins keep the equality form's `orphans_left` at most 0 as their expected range.
- In the statistics profile, the mechanism rules (`lineage`, `representation`) come before the class rules (`hierarchy`, `dimension`), as in retail; otherwise a derivation between two data tables would be `hierarchy`.

**Unknown**

- Nested field paths inside an expression join are not supported (`a.b.c` reads as catalog.table.column); the equality form still supports them.

## 6. Divergences

- The statistics profile orders its rules unresolved, lineage, representation, hierarchy, hierarchy, dimension, not in the order the labels are listed; see section 5.

- The `bad-join-form` schema fixture now tests a two-line join, since `user_id = id` is valid schema-wise and is rejected by the loader instead (tested).
