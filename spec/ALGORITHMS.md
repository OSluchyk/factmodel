# FactModel - Algorithms

Author: Oleksandr Sluchyk · Version 0.1 · 2026-10-23
Companion to `spec/SPEC.md`. Terms are defined in `spec/VOCABULARY.md`; file shapes in `schemas/`.

The core runs three algorithms. All three are pure functions: same input, same output, no I/O, and the order of input files never matters. Test vectors live in `tests/vectors/<algorithm>/<case>.yaml`; each holds the input model files and the expected output.

## 0. Common definitions

**Model.** The set of loaded files: entities (by `id`), relationships (by reference `<entity-id>.<key>`), evidence records (by `id`, inline under `records:` or in `evidence` files), and the profile.

**Effective status of a fact.** Every fact that can carry evidence has an effective evidence status:

1. If the fact says `status: unresolved`, its status is `unresolved`.
2. Otherwise look up the records its `evidence` list names. Its status is the best status among them, in the order `confirmed` > `inferred` > `unresolved` > `retracted`.

So a fact with one confirmed and one inferred record is `confirmed`; a fact whose only record is retracted is `retracted` (the gate's `evidence` stage reports it).

**Usable.** A fact is usable for scope when its effective status is `confirmed` or `inferred`. An inferred fact always has a citation, because an `evidence` list is required unless the fact is explicitly `unresolved`.

**Ends.** A relationship on entity `S` with target `T` has two ends, `S` and `T`. A target set has one pair of ends per target.

**Order.** Wherever the algorithms pick between equals, they sort by entity ID or relationship reference, in plain byte order. Output rows are sorted the same way.

**Generated files.** Every file in `generated/` starts with the header line `# generated by fact project - do not edit`, then a tab-separated column header, then rows. An empty cell is written as `-`.

## 1. Projection

**Input.** Relationships, entities with their class, the scope result (algorithm 2), evidence records, and the profile's ordered rules.

**Facets.** For a relationship `r` with ends `S` and `T`:

| Facet | Holds when |
| --- | --- |
| `evidence_status: v` | the effective status of `r` is `v` |
| `mechanism: v` | `r.mechanism` is `v` |
| `cardinality: v` | `r.cardinality` is `v` |
| `any_end_class: v` | `S` or `T` has class `v` |
| `all_ends_class: v` | `S` and `T` both have class `v` |
| `any_end_subject_scoped: b` | (`S` is scoped or `T` is scoped) equals `b` |
| `all_ends_subject_scoped: b` | (`S` is scoped and `T` is scoped) equals `b` |
| `all_ends_match: [p, ...]` | each of `S` and `T` matches at least one pattern; an end matches a pattern when every key in it (`class`, `subject_scoped`) equals the end's value |

"Scoped" means the end's `subject_scope` is not `none`. A rule matches when every facet in its `when` holds.

**Steps.**

1. **Rule 0 - target sets.** If `to` is a list, project each target on its own (steps 2 and 3 with that target as `T`). If any target is residue, the relationship is residue, with one residue row per such target. Otherwise, if all targets got the same label, the relationship gets it; if not, it gets `withheld`.
2. Evaluate the rules in order. The first rule that matches gives the label. Later rules are not looked at, so two matching rules are a tie that the earlier one wins.
3. If no rule matches, the relationship (or the target) is residue.

**Output.**

- `generated/labels.tsv`: `relationship`, `label`, `targets` (for a target set, `<target>=<label>` per target joined with `, `; else `-`). Residue relationships have no row here.
- `generated/residue.tsv`: `relationship`, `target`. The gate's `projection` stage fails on any row.

**Worked examples** with the retail profile from `profiles/retail/profile.yaml` (rules in order):

| Rule | `when` | Example relationship | Why it matches | Vector |
| --- | --- | --- | --- | --- |
| 1 | `evidence_status: unresolved` | `order_items.sells` with `status: unresolved` | effective status is `unresolved` | `rule-unresolved` |
| 2 | `mechanism: derivation` | `daily_sales.from-orders` (a table computed from orders) | mechanism is `derivation` | `rule-lineage` |
| 3 | `mechanism: representation` | `orders_export.copy-of` (an export of orders) | mechanism is `representation` | `rule-representation` |
| 4 | `any_end_class: administrative` | `load_jobs.loaded` to `orders` | `load_jobs` is administrative | `rule-administrative` |
| 5 | `any_end_class: configuration` | `orders.in-channel` to `channels` (configuration) | `channels` is configuration | `rule-configuration` |
| 6 | `all_ends_match: [{class: data, subject_scoped: true}, {class: reference}]` and `any_end_subject_scoped: true` | `orders.placed-by` to `users`; `order_items.sells` to `products` | both ends are scoped data, or one is scoped data and the other reference | `rule-customer-scoped` |

Other cases:

| Case | What it shows |
| --- | --- |
| `tie` | A derivation from an administrative entity matches rules 2 and 4; rule 2 wins. |
| `residue` | `inventory_items.stored-at` (unscoped data to reference) matches no rule. |
| `target-set-agreement` | Per-tenant target set `[orders, users]`: both `customer_scoped`, so the relationship is `customer_scoped`. |
| `target-set-disagreement` | Target set `[orders, channels]`: `customer_scoped` and `configuration` disagree, so `withheld`. |
| `discriminator` | Discriminated target set `[orders, inventory_items]`: the second target is residue, so the relationship is residue for that target. |

## 2. Subject scope closure

Scope is derived, never authored (D-007). Projection (algorithm 1) reads its result, so the core runs this algorithm first.

**Input.** Entities, relationships, evidence records, and the profile's `anchor_entity`.

**Admitted step.** A relationship `r` on entity `S` with target `T` is an admitted step when all of these hold. If `r` has a `scope_admission` but one of them fails, the admission is rejected with the reason in brackets (`vocabulary:admission_rejection`):

1. `r` has `scope_admission`. Without it, scope does not pass, and nothing is rejected - there was no claim.
2. `to` is a single target, not a target set (`target_set`).
3. `mechanism` is `declared_fk` or `inferred_join` (`wrong_mechanism`).
4. Neither `S` nor `T` has class `reference` (`reference_end`).
5. `r` and its `scope_admission` are both usable (`weak_evidence`).
6. If the basis is `current_row_rule`, `T` has a `current_row_rule` that is not null (`no_current_row_rule`).
7. If the basis is `unique_target`, the cardinality is `many_to_one` or `one_to_one`, so each source row meets at most one target row (`non_unique_target`). A target whose key repeats needs `current_row_rule` or `measured_fanout`.

**Steps.**

1. The anchor entity is `direct`, with no via-path and no basis.
2. An entity with `anchor_reference` (a field name, or a path when the key is nested) whose evidence is usable, and whose class is not `reference`, is `direct`, with no via-path and no basis. Direct wins: an entity that is direct is never transitive.
3. Transitive scope is a breadth-first fixed point. Level 0 holds the direct entities. An entity that is not yet scoped joins level `k + 1` when it has an admitted step to an entity at level `k` or lower. If it has several, it takes the one whose target has the lowest level, then the lowest relationship reference. Its via-path is that relationship followed by the target's via-path; its basis is that step's basis.
4. Repeat until a level adds nothing. Every entity not scoped by then is `none`. A cycle of admitted steps that never reaches a direct entity stays `none`; a cycle that does reach one stops at the first level where each member is scoped.
5. An entity of class `reference` is always `none`, and an `anchor_reference` on it is reported as a rejection (`reference_end`).

**Reachable.** An entity is reachable when a path connects it to the anchor. The edges are relationships, walked in either direction, using every target of a target set, and skipping relationships whose effective status is `unresolved` or `retracted` and those with mechanism `derivation`; and usable `anchor_reference`s, each an edge between its entity and the anchor. Reachability does not need admissions: a reference entity such as `products` is reachable but never scoped.

**Output** (`generated/scope.tsv`, one row per entity):

| Column | Value |
| --- | --- |
| `entity` | Entity ID |
| `subject_scope` | `direct`, `transitive` or `none` |
| `basis` | Basis of the first step for `transitive`, else `-` |
| `via` | Relationship references from the entity to a direct entity, joined with ` > `, else `-` |
| `reachable` | `true` or `false` |

Rejections are a second output (`generated/scope-rejections.tsv`: `fact`, `reason`), where `fact` is a relationship reference or `<entity-id>.anchor_reference`. An `anchor_reference` that is not usable is rejected with `weak_evidence`. The gate's `scope` stage fails on any row.

**Worked example** (`tests/vectors/scope/chain-of-three.yaml`). Anchor `users`. `orders` has `anchor_reference: {field: user_id}`: level 0, `direct`. `order_items.part-of` targets `orders` with `scope_admission: {basis: unique_target}`: level 1, `transitive`, via `order_items.part-of`, basis `unique_target`. `item_returns.of-item` targets `order_items` with `basis: current_row_rule`, and `order_items` has `current_row_rule: deleted_at IS NULL`: level 2, via `item_returns.of-item > order_items.part-of`, basis `current_row_rule`.

| Case | What it shows |
| --- | --- |
| `direct` | `anchor_reference` makes an entity direct; the anchor is direct; direct wins over an admitted step; a weak `anchor_reference` is rejected. |
| `chain-of-three` | Scope passes through two admitted steps; via-path and first-step basis. |
| `cycle` | A cycle attached to a direct entity resolves; a detached cycle stays `none`. |
| `reference-blocks` | A step into or out of a reference entity is rejected (`reference_end`); the reference entity is reachable but `none`. |
| `missing-admission` | A usable join to a scoped entity without `scope_admission` carries no scope and is not a rejection; an admission on a retracted relationship is rejected (`weak_evidence`). |
| `two-paths` | Two admitted steps at the same level: the lower relationship reference wins, with its basis; a target at a lower level beats a lower reference. |
| `rejections` | Basis `current_row_rule` on a target without a rule (`no_current_row_rule`), an admission on a target set (`target_set`) and on a derivation (`wrong_mechanism`). |
| `non-unique-target` | Basis `unique_target` on a `many_to_many` link is rejected; `measured_fanout` on the same link is admitted. |

## 3. Release partition

**Input.** The release allowlist (`release-allowlist` file) and every file in the model repository, with its path relative to the repository root and, for YAML model files, its kind and top-level keys.

**Patterns.** A pattern is a path glob: `*` matches any characters inside one path segment, `**` matches any number of whole segments (including none). Patterns are tried in order; the first match wins.

**Steps.** For every file, sorted by path:

1. Find the first matching pattern. If none matches, the file fails with `unmatched`.
2. `export`: the file is released as it is.
3. `refuse`: the file is not released.
4. `project`: the file must be a model file whose kind has a key list in `keys`, else it fails with `no_key_list`. Each top-level key must be in `keep` or `drop`; a key in neither fails with `undeclared_key`. The released copy holds only the `keep` keys, in their original order.

The release is built only when no file fails (`vocabulary:release_failure`). Every file gets exactly one disposition or one failure - the partition is complete.

**Output.** Per file: `path`, `disposition`, and for projected files the kept keys; plus the list of failures (`path`, `reason`, and `key` for `undeclared_key`).

**Worked example** (`tests/vectors/release/complete.yaml`). Patterns `physical/entities/*.yaml → project`, `registers/hazards/*.yaml → export`, `drafts/** → refuse`, `** → refuse`. `physical/entities/orders.yaml` is projected and keeps `kind, id, ...`, dropping `records`; `registers/hazards/H-0001.yaml` is exported; `drafts/new.yaml` and `CHANGELOG.md` are refused. No failures.

| Case | What it shows |
| --- | --- |
| `complete` | Every disposition; first match wins; dropped keys leave the copy. |
| `residue-file` | Without a catch-all pattern, an unlisted file fails with `unmatched`. |
| `undeclared-key` | A projected entity with `extensions` that is in neither `keep` nor `drop` fails with `undeclared_key`. |
